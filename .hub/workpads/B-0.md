# B-0 — gcdfo docs-widoco seeds its own baseline, so a failed build goes green over raw output

Queue item: `B-0` (defect, P3, stream S6, repo `dfo-salmon-ontology`, legacy "item 0").
Evidence pointer: `knowledge/backlog.md` in the metasalmon hub; the repository-local
record was the 2026-08-16 entry in `docs/tech-debt.md`.
Claim token `a-1bb40ea5848c7e06`, branch `agent/B-0/a-1bb40ea5848c7e06`.

Implements option **(b)**, ruled by Brett 2026-09-14. Option (a) — sourcing the
baseline from git HEAD — is rejected and is recorded as rejected rather than
silently dropped, because it was the *stated* intended fix in `docs/tech-debt.md`
and deleting it would have left the repository teaching a discarded option.

## What changed and where

- **`Makefile`**, `docs-widoco` recipe. The recipe keeps the working-tree baseline
  (that is the deliberate property, and the reason option (a) was rejected) and now
  arms a shell `trap … EXIT` that restores the pre-run bytes of
  `docs/webvowl/data/ontology.json` on any non-zero exit. Mechanics:
  - a `WEBVOWL_JSON` variable replaces three literal repetitions of that path;
  - `PRERUN` records whether the file existed before the run, and holds the restore
    source when it did. It is the copy the recipe already takes for the normalizer,
    so the restore is byte-exact and free;
  - on failure the trap announces itself on stderr, then copies the pre-run bytes
    back, or removes the file if there was none before the run;
  - `trap - EXIT` disarms it as soon as the normalizer succeeds — past that point the
    file holds normalized output and every remaining command is cleanup, so leaving
    the trap armed would let a failure in the trailing `rm`s restore from a baseline
    the success path has already deleted;
  - the normalizer branch now keys off `PRERUN` rather than re-testing `BASELINE`, so
    one variable decides both the baseline argument and the restore source. Two tests
    of the same condition was how the fix could have been made to look correct while
    disagreeing with itself.
  - A comment above the recipe carries the reasoning, what the trap does **not**
    cover, and its retirement condition.
- **`docs/adr/010-docs-widoco-restores-prerun-webvowl-baseline.md`** (new). The
  repository's AGENTS.md requires an ADR when choosing between competing approaches,
  and ADR-007 is where the previous decision on this same artifact lives, so this is
  where the repo keeps rejected-option history. Records the decision, the rejected
  git-HEAD alternative and why it was rejected, the consequences (including that
  nothing automated checks the trap still works), and the reproduction table.
- **`docs/tech-debt.md`**. The 2026-08-16 entry moved from *Active* to *Resolved*
  with a resolution, an explicit paragraph recording that its own stated **Intended
  fix** was the rejected option, and a lesson. Deleting it was not enough and leaving
  it was worse.
- **`docs/entrypoints.md`**, **`docs/context/widoco.md`**. Both described the recipe's
  failure behaviour and both are now complete. Both also said the normalizer compares
  against "the prior tracked baseline" / "the previously tracked copy", which is the
  one distinction this whole item turns on — the baseline is the **working-tree** copy,
  which is why a failed run can poison it. Corrected in place.
- **`CHANGELOG.md`**, a new `### Fixed` block under `[Unreleased]`.

No regeneration of `docs/webvowl/data/ontology.json` is part of this change; it is
byte-identical to `main`, which the runs below confirm.

## Commands and results

Toolchain, checked before claiming because the item says the verification cannot run
without it: `java` 21.0.10 present; `tools/widoco.jar` (1.4.25) and `tools/robot.jar`
(1.9.8) absent and fetched with the repo's own `make install-widoco` /
`make install-robot`; `rsync` absent and installed (the recipe needs it); no sibling
`salmon-domain-ontology` checkout, so `prepare-import-catalog` took its documented
`SMN_PIN` fallback (`f7205ee`).

**Control, before any change** — unmodified recipe, `make docs-widoco`: exit 0, and
`docs/webvowl/data/ontology.json` byte-identical to the committed file. So a green run
was green here for the right reason before the change, and the induced failures below
are the change under test rather than the environment.

**The four required steps.** Run against both variants, because the item is explicit
that a clean run twice is necessary and not sufficient, and that breaking the build
proves nothing on its own — the unfixed recipe fails identically at that step. The
injected failure is `raise ValueError(...)` at the top of `Normalizer.normalize()`,
the same shape as the abort ADR-007 repaired: it crashes after `rsync` has already
overwritten the artifact.

| step | unfixed recipe (`main`) | with the trap |
|---|---|---|
| 1–2. break normalizer, `make docs-widoco` | FAILS — `ValueError`, `make: *** [Makefile:259: docs-widoco] Error 1`, exit 2 | FAILS — `ValueError`, trap prints `↩️  docs-widoco failed (status 1); restoring the pre-run docs/webvowl/data/ontology.json …`, `make: *** [Makefile:283: docs-widoco] Error 1`, exit 2 |
| 3. state of the artifact | `sha256 3201d305a07959e1…` — **raw WIDOCO output**; `git status` ` M docs/webvowl/data/ontology.json` | `sha256 baa1dc69ba550c2d…` — **pre-run bytes**; `git status` clean |
| 4. repair normalizer, re-run | exit **0** — `sha256 567a9dcb290a0352…`, still dirty, **8219 lines changed** against the committed artifact: green over raw bytes | exit **0** — `sha256 baa1dc69ba550c2d…`, `git status` clean: green on correctly normalized bytes |

Step 4's unfixed hash is neither the committed file nor step 3's raw bytes but the raw
bytes of the *second* generation: the poisoned baseline was raw, the fresh raw output
was semantically equal to it, so the normalizer restored the fresh raw ids. Every
later run repeats that, each exiting 0, which is why this was only ever going to be
found by inspection.

**Clean double-run with the final recipe**, the necessary-but-not-sufficient half:
`make docs-widoco` twice, exit 0 both times, `docs/webvowl/data/ontology.json`
`baa1dc69ba550c2d…` after each and `git status` clean for it, so the trap has not
disturbed byte-stability.

`make -n docs-widoco` output was extracted and `sh -n`-checked before the first run —
the trap body is one physical line on purpose, because a backslash-continued make line
inside single quotes is not a shell line continuation.

Running `docs-widoco` alone also rewrites `docs/index.html` and `docs/index-en.html`,
because `docs-skos` and `docs-postprocess` (the rest of `docs-refresh`) are what put
the repo's own post-processing back. That is pre-existing and unrelated; those two
paths were reset between runs so they could not be mistaken for a result.

## What I did not do, and why

- **Nothing was pushed, and no pull request was opened.** `dfo-salmon-ontology` is a
  shared member repository — two other participants, another organization — so the
  grant in `HUB.md` does not cover a branch push or a draft PR here. The work ends at
  this branch in the worktree plus the PR text handed to Brett in chat.
- **No CI regression test for the trap.** Making CI prove the trap still works means
  injecting a normalizer failure into a `make ci` run, which is a new gate rather than
  this fix. ADR-010 records the gap under *Consequences → Negative* instead of
  implying coverage that does not exist, and the reproduction above is the manual
  check. New-item candidate below.
- **Only `docs/webvowl/data/ontology.json` is restored**, not the other files `rsync`
  copies into `docs/`. Brett's ruling names that path, and it is the only one that is
  its own baseline; the others cannot poison a later comparison and the CI drift check
  covers them.
- **`docs/webvowl/data/ontology.json` was not regenerated or re-baselined.**
- **No commit attribution trailers.** This repository's `AGENTS.md` says, as a
  non-negotiable: "Do NOT add 'Co-authored-by …' lines or any hidden authorship
  markers unless the user explicitly requests it." That is a project instruction in
  the repository the commit lands in, so it wins over the session default. Flagged for
  Brett; `git commit --amend` reverses it in one command if he wants them.

## Belongs to another item / new-item candidates

- **New-item candidate: `prepare-import-catalog` is a live instance of the fault class
  AGENTS.md records, and it is a dependency of `docs-widoco`.** The fault AGENTS.md
  names ("a `make` recipe whose missing `set -e` printed a success mark over a
  crashing script") is *this* recipe's own history, fixed 2026-08-16 along with
  `release-snapshot` (ADR-007, *More Information*). Both still carry `set -e`; that is
  not regressed. But `prepare-import-catalog` has the identical shape and no `set -e`:
  a `;`-chained block whose every branch ends in `echo "✅ ROBOT catalog maps smn
  import to …"`, so make takes the `echo`'s status. Demonstrated by making the real
  recipe's real `printf > $(ROBOT_CATALOG)` fail — the write fails, the success mark
  prints, and `make` exits **0**. The consequence is worse than a wrong mark, because
  every ROBOT target and `docs-widoco` itself consume that catalog: a half-written or
  unwritten catalog changes how the `smn` import resolves, which changes the published
  artifacts. Nine further recipes lack `set -e` but are single logical commands split
  across continuations, or `if`-blocks whose status does propagate; this one is the
  instance worth an item. Not fixed here — out of this item's `retires_when`.
- **New-item candidate, and the more serious of the two: the `pre-push` hook in
  `.pre-commit-config.yaml` cannot fail, and it discards this very artifact.** Its
  `entry` is one `bash -lc` chain with no `set -e` that ends
  `…; make ci; git checkout -- docs/webvowl/data/ontology.json || true`. Two
  consequences, both verified:
  - **The hook's exit status is always 0**, because it is the status of the trailing
    `|| true`. A failing `make ci` therefore does not fail the pre-push gate.
    Reproduced with the same tail shape: `bash -lc 'make definitely-not-a-target;
    git checkout -- README.md || true'` prints make's error and exits **0**. This is
    the fault class AGENTS.md names, in a live guard rather than in history.
  - **The `git checkout --` unconditionally throws away whatever `make ci` produced
    for `docs/webvowl/data/ontology.json`**, on success as much as on failure. The
    hook fires only when `ontology/dfo-salmon.ttl` changed (`files:`,
    `stages: [pre-push, manual]`) — precisely when that artifact most likely *should*
    change. It is a no-op in the intended flow, where the regeneration is already
    committed, and it silently drops a legitimate regeneration when it is not, after
    which CI's drift check fails for a reason the hook has erased the evidence of.
  - It reads as a pre-normalizer churn suppressor that outlived its cause — the same
    shape as the CI exclusion that AGENTS.md records as having been added five weeks
    before the normalizer whose crash it went on to hide — and it states no
    retirement condition. The trap landed here removes the failed-build rationale for
    the `git checkout --` line, which is what makes it worth an item now.
- No other queue item's scope was entered.

## Retirement conditions of what I added

- **The trap in `docs-widoco`** retires when the recipe stops overwriting the file it
  uses as its own baseline — for instance normalizing inside `release/tmp/widoco` and
  copying only normalized bytes into `docs/`, which removes the window instead of
  repairing it afterwards. It does **not** retire by adopting the rejected `git show
  HEAD:` baseline. Written above the recipe and repeated in ADR-010, and ADR-010 also
  states what the trap does not cover: a shell killed by a signal, where no `EXIT`
  trap runs and `git checkout -- docs/webvowl/data/ontology.json` is still the repair.
- **ADR-010** retires with the trap, as a superseded ADR, if a later decision removes
  the window; it is the record of a rejected option, so it is not deleted when that
  happens.
- No suppression, exclusion, allowlist entry or skip was added.
