## What changed, and where

One file: `.pre-commit-config.yaml`, the `ontology-ci` hook. 39 insertions, 7
deletions — most of it a comment block; the behavioural change is the tail of
one `entry` line.

Before, the `entry` chain ended:

```
... else make ci; fi; git checkout -- docs/webvowl/data/ontology.json || true
```

After:

```
... else make ci; fi; ci_status=$?; if [ "$ci_status" -ne 0 ]; then git checkout -- docs/webvowl/data/ontology.json; fi; exit "$ci_status"
```

That one edit closes both halves of the defect.

**(a) It could not fail.** A shell returns the status of the last command in the
list. The last command was `git checkout -- … || true`, which is 0 whether the
checkout succeeds or fails, so the hook exited 0 for every build including
failing ones. `ci_status` now captures the build's status immediately and the
chain ends `exit "$ci_status"`.

**(b) It discarded a build product.** `make ci` regenerates
`docs/webvowl/data/ontology.json` — the path is inside `CI_ARTIFACT_PATHS` in
the `Makefile` — and `.github/workflows/ci.yml` rejects *any* uncommitted change
left after `make ci` across the whole worktree. The hook's `files` pattern
restricts it to changes to `ontology/dfo-salmon.ttl`, which is precisely when
that artifact is expected to change, so the unconditional checkout threw away
locally exactly what CI then demanded. The restore now runs only on the failure
path.

**The failure-path restore is kept on purpose, and that is what makes half (b)
safe without waiting for B-0.** `docs-widoco` rsyncs raw WIDOCO output over
`docs/webvowl/data/ontology.json` before the normalizer runs, so a build that
dies in between leaves raw generator bytes in the tree that a later run adopts
as its normalizer baseline and goes green over. That is B-0, and
`docs/tech-debt.md`'s 2026-08-16 entry ("A failed `make docs-widoco` can
re-baseline WebVOWL output to raw generator bytes") prescribes exactly this
restore as the local remedy — **"before retrying a failed docs build"**, not
after every push. Scoping the checkout to the failure path therefore preserves
the whole of its remaining rationale while removing the harm, so B-150's
sequencing note is satisfied by the second of its two options: recorded as safe
without B-0 rather than deferred behind it.

### One observation about the harness, worth recording

`pre-commit` exits 1 on a *successful* build whenever the hook modified files
("files were modified by this hook"). That is the harness's own check, not the
hook's exit status, and it is correct behaviour: it means an ontology change is
being pushed whose regenerated artifacts are not committed, which is what CI's
drift gate would reject. It masked nothing before the fix and masks nothing
after, but it is why reading a `pre-commit` exit code alone cannot tell you
whether the gate works — the two reproductions above separate the build's status
from the harness's by using a failure that never reaches the docs step.
