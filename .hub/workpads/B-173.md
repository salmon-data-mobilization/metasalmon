## Which fix, and why

The item names two, and says which cases each catches. They are not variants of
one idea:

- **A — compare the parsed value against the raw text and refuse when what was
  removed is not a comment.** General: it asserts an invariant (*the thing the
  client reads is the thing on the page*) rather than banning a character.
- **B — refuse an unquoted value containing a hash at all.** Blunter, and it
  needs no judgement about what a comment looks like, so it also catches a
  truncation whose tail happens to be comment-shaped.

**Chosen: A.** Three reasons, in the order they decided it.

1. **B cannot be done inside this item.** It requires deleting
   `test_trailing_comment_is_stripped_from_unquoted_values`
   (`scripts/tests/test_hub_queue.py:288`), which pins the trailing-comment form
   the schema block documents. `HUB.md` § *Which pull requests need Brett*,
   class 6: *"It relaxes, narrows, disables, or deletes a guard, test, skip
   condition or validator. Adding one is delegated; weakening one is not."*
   Deleting a documented capability and its test is his call, not a by-product
   of a P3 defect fix. A is delegated; B is not.
2. **B has a false positive on a documented feature that has nothing to do with
   this defect.** `check_evidence_exists` documents
   `evidence: knowledge/backlog.md#B-53` as a working pointer, and says in as
   many words that it survives *because* the parser cuts on space-hash and there
   is no space here. A blanket hash ban breaks that with nothing failing to say
   so; A never sees it, because nothing is removed.
3. **A matches the measured exposure.** The item measured it and this branch
   re-measured it: the construction that bites is `#N` welded to the hash, and
   it is the construction these fields are full of because every migrated item
   cites one.

The discriminator is the character straight after the hash: `#` then whitespace,
or a bare `#` at end of line, is a comment; `#` welded to anything else is
content. That is not a new judgement — `parse_scalar` already refuses an unquoted
value that *begins* `#` and tells the author to write `legacy: '#53'`. This is
the same rule with the position restriction dropped, and both messages point at
the same remedy.

**What A does not catch, and it is in the source rather than only here.** A tail
that is comment-shaped but was meant as content still disappears silently —
`title: Fix the renderer # 32 of these were wrong` becomes `Fix the renderer`.
Closing that is exactly fix B, which is the decision above. Recorded in
`comment_loss_problem`'s docstring under **WHAT IT DOES NOT CATCH**, because a
guard whose claimed scope exceeds its real scope is worse than no guard.

## What changed and where

### `scripts/hub_queue.py`

- **`split_comment(value) -> (kept, removed)`** (new). The cut, with `removed`
  returned instead of dropped, so a caller can ask what is about to be thrown
  away. `strip_comment()` is now `split_comment(value)[0]` — same bytes, same
  callers, no behaviour change, so `read_config_member_rows` is untouched.
- **`looks_like_a_comment(removed)`** (new). The one discriminator, with the
  argument for it.
- **`comment_loss_problem(kept, removed)`** (new). Returns the refusal message or
  `None`. Carries the evidence, the scope, the case it misses, and the
  retirement condition.
- **`parse_scalar`** returns `(value, error, rule)` instead of `(value, error)`,
  so the new refusal is reported under its own rule name rather than folded into
  the generic `value`. One caller, updated. Every pre-existing error path keeps
  the rule `value`, so no existing message or rule name moved.
- The check sits **once, above the unquoted branches**, not beside the
  plain-scalar one. All three unquoted branches — flow list, boolean, plain
  scalar — read through the same cut, so a check placed on the scalar branch
  alone would let `blocked_by: [B-90] #124 is next` keep losing its tail on a
  path it never reaches. Pinned by
  `test_the_flow_list_branch_is_covered_too`.
- **Scope: every key, not only `title` and `retires_when`.** The item set those
  two as a floor. A rule whose scope a reader has to take on trust is worse than
  one that applies everywhere, and the sweep says it costs nothing: 131 item
  files, **zero** unquoted values containing a hash of any kind and **zero**
  trailing comments.
- The schema block at the top of the file documents the new refusal, in the
  paragraph that already documents the cut. That block is the one home of this
  rule; the only other copy in the repository is
  `knowledge/backlog.md`'s evidence entry for this defect, which describes the
  defect rather than the rule and stays as the record.

### `scripts/tests/test_hub_queue.py`

`TestTruncationIsNotSilent`, twelve tests. Eight are RED demonstrations; four are
green-side pins that pass before *and* after, on purpose — they are what stops
this fix being fix B by accident (the trailing comment, the bare `#`, the
no-space `#fragment`, and a trailing comment after a quoted value).

The class header says the RED demonstration is **reconstructed, not taken from
the tree**: `B-124` and `B-125` were quoted in the change that filed `B-173`, so
the queue no longer holds an example. The sweep over the real queue is the other
half of the evidence and it is below, because that file writes only into a
temporary directory.

## Candidates, no item

- **`parse_scalar`'s `"value is only a comment"` branch is unreachable, and was
  before this change too.** Not absorbed, and stated with the evidence because
  `AGENTS.md` names this shape as a hazard: *duplicate placement guards in
  `migrate_sdp_methods()` that became unreachable when the real checks moved
  earlier, leaving dead code that invited someone to weaken the live copy.*
  Reached only when `split_comment` leaves an empty value, which cannot happen:
  `text` is already `.strip()`ed, so `find(" #")` can never return 0, so the kept
  half always holds at least `text[0]`; and a value that is *entirely* a comment
  starts with `#` and is caught two branches earlier by
  `value begins with '#'`. Probed on this branch — `' # note'`, `'  #'` and
  `'#note'` all return the begins-with-hash error; nothing returns this one. The
  reordering here did not create that: the same argument holds against `HEAD`,
  where `strip_comment(text)` was computed lower down but from the same `text`.
  Deleting it is a one-line change with no behaviour attached, which is why it is
  a candidate rather than something to slip into a defect fix.

- **`read_config_member_rows` strips a trailing comment from `members:` fields in
  `queue/config.yaml` with the same silence**, at `scripts/hub_queue.py`'s single
  remaining `strip_comment` call site. Deliberately not swept into this fix:
  B-173's `retires_when` is about item-file values, and `HUB.md` says a second
  problem is a new queue item rather than a widened one. **Evidence for why it is
  a candidate and not an item**: the four fields there are enumerated or
  cross-checked — `repo` and `org` against the domain card's allowlist, `solo`
  against `HUB.md`'s participation table, `forge` against two literals — so a
  truncation that changed a value would fail one of those cross-checks loudly
  rather than pass. The residue is a truncation that leaves a *still-correct*
  value, which changes nothing. Worth an item only if that block ever grows a
  free-prose field; it has none today.

## Retirement conditions of what this adds

- **`comment_loss_problem` / `looks_like_a_comment` / rule `truncated-value`.**
  *Retires when:* `split_comment` stops being able to lose anything — either
  because the schema requires `title` and `retires_when` to be quoted outright,
  or because the reader stops honouring a trailing comment on an unquoted value
  at all (which is fix B). Either change means no value can be truncated, at
  which point this rule and `looks_like_a_comment` are **deleted**, not kept as a
  check that can no longer fire. Written into the function's docstring, which is
  where a reader of the guard will be.
- **`TestTruncationIsNotSilent`.** Retires with the rule it demonstrates, under
  the file's own standing condition: *"A rule removed from the linter must have
  its pair removed here in the same change."* Its four green-side pins retire
  with the capabilities they pin, not with the rule — if fix B is ever taken,
  `test_hash_then_a_space_is_a_comment_and_still_works` and
  `test_a_bare_hash_at_end_of_line_is_a_comment` are the two that have to go,
  and that is the visible cost of taking it.
- **No suppression, skip, exclusion or allowlist entry was added**, so there is
  nothing else here that could outlive its cause.
