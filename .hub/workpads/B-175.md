### Why this shape

1. **Fix the shared accessor, not the call sites.** `.ms_metadata_schema_fields()`
   is the one read the scan, the setters and the validator's blank-required
   collector share, so reading the bundle there removes the fetch from all of
   them.
2. **A separate cache slot, not `.ms_load_sdp_schema(source = "vendored")`.**
   The loader's cache is one slot keyed by source, so a vendored read through it
   evicts the session's `auto` bundle. The next writer, reader or validator
   call then fetches all eight documents again. A script could also stamp two
   packages with different profile identities, which is the exact property the
   loader's comment says it caches the fallback to protect. metasalmonpy reads
   its bundled documents outside its loader cache for the same stated reason.
   Test 2 pins this, and RED demonstration 2 shows that the naive fix fails it
   while passing the network test.
3. **The validator's blank-required collector follows, deliberately.**
   `.ms_collect_blank_required_metadata_fields()` (`R/package-helpers.R`)
   reaches the accessor through `.ms_schema_required_metadata_fields()`, and its
   own comment claims *"read from the same schema parse [`review_metadata()`
   reads], so the two cannot disagree about which fields block"*. Moving only
   the scan would have made that comment false. metasalmonpy made the same
   choice explicitly (`package_io.py`, `source=_SCHEMA_SOURCE`). **No result
   changes today**: measured below, the bundled and published copies of all six
   metadata schemas are identical.
4. **Superseded by the Codex round: no option is ignored any more.** This point
   first read *"No warning when `metasalmon.sdp_schema_source` would be
   ignored"*. It defended reading the bundle whatever the options said, on the
   grounds that the options are documented to no user and that the port has no
   warning. Codex showed that the ignored options are the writers' field
   contract (see below). The accessor now honours any non-default schema
   setting, so there is nothing left to warn about.

### Codex review of #145 at `2b74b14`: one finding (P2), fixed locally

The finding, thread `PRRT_kwDOSoVfrc6lNfgN` at `R/sdp-field-setters.R:119`:
*"Honor the configured schema when editing metadata."* When
`metasalmon.sdp_schema_base_url` or `metasalmon.sdp_schema_source` resolves a
valid bundle whose fields differ from the vendored copy, the writers use that
bundle. The hard-wired vendored read then made `review_metadata()` omit its new
requirement and `set_sdp_dataset(new_field = ...)` refuse the field. This
happens even after `create_sdp()` has cached the configured bundle, so honouring
it needs no request.

This round was prepared **locally only**. The coordinator paused the protocol
before it started, so nothing was pushed, no thread was answered or resolved,
and no claim-ref write was made. The reply is drafted outside the repository.

**Reproduced before deciding.** A base URL option named a valid bundle that
adds one required `dataset.csv` field, `funding_source`, cached under the
writers' own key as `create_sdp()` leaves it. The fetch was replaced by a
counter:

```
2b74b14 (as pushed)                          main 12efe9d (before the PR)
writer writes funding_source column: TRUE    TRUE
review_metadata reports it:          FALSE   TRUE
set_sdp_dataset(funding_source=..):  ERROR 'dataset.csv' has no such field   accepted
validator blank-required collector:  FALSE   TRUE
remote fetches: 0                            0
```

So it is a regression this PR introduced, and a wider one than Codex named:
the validator's blank-required check lost the field too, because it shares the
accessor. The item's `retires_when` is scoped to *"the shipped default
options"*, so nothing required changing behaviour outside them.

**Decision: honour any non-default schema setting through the loader, as `main`
did, and read the bundle only under the default options.** The coordinator
suggested a different shape: read the configured schema only when it is already
cached, and otherwise read the bundle. I did not take it, for three reasons:

1. **It makes the answer depend on call order.** The same call, with the same
   options on the same package, would return two different field contracts
   depending on whether a writer happened to run earlier in the session.
2. **In a fresh process it still hits the finding.** A scripted review that
   starts a new R process per package is the case this item names. There,
   nothing is cached, so the configured schema would silently be replaced by
   the bundle.
3. **`AGENTS.md` says an option that will be ignored should warn rather than
   silently no-op**, and that shape ignores a set option whenever the cache is
   cold.

Under the loader branch, a schema the session has resolved costs nothing and is
not evicted, because the key is the writers' own. A published schema not yet
resolved is fetched once, as a writer would fetch it. Selecting one is the
opt-in, the same shape as `llm_assess = TRUE`. The zero-request promise stays
exactly as wide as the item requires, and the roxygen and NEWS now say so.

The other implementation differences are internal and have no observable
behaviour:

- R reads the validated bundle, cached in its own slot. Python reads the raw

- R chooses the source in one place, `.ms_metadata_schema_fields()`, by asking

  through four accessors.
- R's second guard is a proxy listener. Python's patches the socket API. Both
  are client-independent, and R's scope limit is written in its test header.
- R's setter documentation states the no-network property. Python's setter
  docstrings do not; its module docstring and `review_metadata()` docstring do.

The other Python-side candidate is the missing `set_sdp_code()` assertion
above.
