# Workpad — B-187

## Queue item

**B-187** — `hub` reads the queue from whatever checkout it is run in, and says
an item does not exist when the tree is stale (kind defect, repo metasalmon,
severity P2, stream S15, venue claude-code, `blocked_by: []`). Claimed by
`a-cdac1171a618da39` on 2026-09-24 at 13:06:35Z; work branch
`agent/B-187/a-cdac1171a618da39`, worktree
`hub-worktrees/salmon-data-mobilization-metasalmon-B-187`, created from
`origin/main` at `43d7fb3`.

Scope is the item's `retires_when`, which has three parts, and this branch
answers each:

1. `scripts/hub` refuses, or warns by name, when the checkout it reads the queue
   from is behind the remote default branch, and the message names staleness,
   the distance and the branch.
2. Demonstrated RED by running `claim` against an item that exists on
   `origin/main` and not in the working tree.
3. **The fix cannot live only in the client**: something independently current
   has to run before the checkout-local client, and the demonstration that
   means anything is RED from a checkout that predates the fix.

## Which fix, and why

**Client side: refuse, not warn, for the commands that answer from the queue.**
The item offered both. Refusal was chosen for `claim` because a claim is a
write on the queue's rules, and the client already fails closed on every other
precondition it cannot verify (the cap, the reclaim limit); `reconcile` refuses
for the same reason, since it expires other agents' claims under a grace read
from the checkout. It was chosen for `ready` because `ready` succeeding on a
stale tree is the half of the defect the item calls worse. `beat` and `release`
go ahead and `done` only warns, because each records this agent's own claim and
a heartbeat refused over an unrelated merge would cost a lease. **But every
command that pushes checks where the push goes** — `locks_repo` and
`claim_ref_prefix` against `origin`'s — and refuses on a difference. The first
version of this change said those three commands "read no queue file", which
was false, and Codex's first review found it; see *Codex review* below.

**It asks origin, not the checkout.** A checkout's own `origin/main` is only as
current as the last fetch made there, so in a checkout nobody fetches in it is
as old as the branch and says "current". Measured today rather than assumed: a
fetch at 17:37Z left `origin/main` at `2d28478`, and a minute later `origin`
reported `3bc943b`.

*(Corrected 2026-09-24: this paragraph first said that in the 2026-09-16
checkout `origin/main` "was as old as the branch, because nobody had fetched
there either". That was an explanation written from memory, and the primary
checkout's reflog refutes it: `refs/remotes/origin/main` was fetched eleven
times between 01:34Z and 03:24Z that night, and B-187 was filed at 03:31Z. So
a comparison with the local ref would very likely have caught that incident too;
the case for asking `origin` is the general one above, not that incident. The
same sentence was corrected in `scripts/hub`, `HUB.md` and the pull request
description.)*

`git ls-remote --symref origin HEAD` names the default branch and its tip; if
the checkout already contains the tip nothing is fetched at all; otherwise the
branch is fetched for its **objects only** (`--refmap=` with no destination,
`--no-write-fetch-head`, `--no-auto-gc`), so the caller's `origin/main`,
`FETCH_HEAD` and branches are exactly as they were. That matters because it runs
in whatever checkout the caller stood in, and that can be Brett's primary
checkout. Measured in a scratch repository before writing it: the fetch leaves
`for-each-ref` identical and writes no `FETCH_HEAD`.

**The bootstrap half: `hub fresh [PATH...]`, run by whoever names a checkout.**
A checkout old enough to mislead carries a client too old to ask, so the answer
has to come from a client newer than the checkout. `fresh` asks the same
question of a named checkout, using only that checkout's git and origin — it
never runs the named checkout's client and never reads its queue. `HUB.md` now
says an orchestrator runs it from its own checkout against every checkout a
dispatch brief names, at dispatch, and names only one that passes.

It is a **new verb rather than a line in `doctor`** on purpose. Asked for
`fresh`, a client that predates the check exits 3 with `unknown subcommand`,
which is loud; asked for `doctor`, the same old client passes, having never
heard the question. So even an orchestrator that runs the check with the wrong
checkout's client gets a failure rather than a false pass.

The alternative the item names, "a refresh enforced at that point", was not
taken: refreshing a dispatch path means moving a primary checkout, which is
Brett's workspace (`HUB.md` § *Isolation*).

## What changed and where

### `scripts/hub`

- **`checkout_freshness DIR`** (new): current, stale, or cannot tell, with the
  distance, both branches and both tips, into `FRESH_*` globals. It cannot tell
  when DIR is not the root of a git checkout, has no `origin`, `origin` cannot
  be read or fetched, or `origin` names no default branch.
- **`require_current_queue MODE [ID]`** (new): the one call every queue-reading
  command makes first. `refuse` for `claim` and `reconcile` (stale or cannot
  tell: exit 3); `refuse-stale` for `ready` and `ready --set` (stale: exit 3;
  cannot tell: warn and list, as `ready` already does when the locks repository
  cannot be read); `warn` for `done`. With an ID, a refusal also says what
  `origin` has for that item — **"B-187 is not in this checkout, and it IS on
  origin/main"**, or both states when they differ.
- **`require_routing`** and **`routing_differs`** (new, from Codex's first
  review): every command that pushes — `claim`, `beat`, `release`, `done`,
  `reconcile` — compares `locks_repo` and `claim_ref_prefix` with the
  configuration on `origin`'s tip before its first push, and exits 3 on any
  difference, whether the checkout is behind, ahead or edited in place. `done`
  does it before the handoff, not after. **`repo_freshness`** caches the answer,
  so one invocation still asks `origin` once.
- **`absent_item_sentence`** (new): "no queue item X" now says it is speaking
  for the queue only when the checkout was checked and found current, and for
  the checkout alone when it could not be compared.
- **`cmd_fresh`** (new verb), wired into `main` and `help`.
- **`cmd_doctor`** reports the answer as a line of its own, last among the
  network checks so it cannot stop the locks-repository probes running, then
  the routing as a second line, and its "not verified" list says the answer
  ages.
- **`yaml_scalar_stream`** (new): the existing extractor, split so the same awk
  program can read an item file out of a commit. `yaml_scalar` now calls it with
  the file on stdin; same program, same output.

### `scripts/tests/test_hub_claim.sh`

- **Assertions 35 to 41** (below). Numbered from the next free label, per the
  file's own rule. 41 is the routing, from Codex's first review.
- **Every fixture queue is now a git checkout** with a bare `origin` beside it
  (`make_checkout`), because `claim` refuses from anything it cannot compare
  with `origin`. No assertion's condition changed; the pre-existing 34 pass
  against both the old and the new client on the converted fixtures (see the

- **`run_with_timeout` stops its watchdog with SIGKILL**, closing a race that

### A race in the test harness, which this change exposed and fixes

With the new fixtures and before the harness fix, the suite was **flaky**, and
the cause is older than this branch. Over one hour, in the isolated clone, it
failed five times in twenty-four runs: four died in setup (`FATAL could not make
…/cap-fixture-repo a git checkout with an origin`, `could not build the
predates fixture`, `could not build the stale-checkout fixture`, and the same
for the refuse fixture) and one reported `passed 8 failed 11 skipped 21`.

`run_with_timeout` backgrounds each command beside a watchdog subshell and, when
the command finishes first, stops the watchdog with **SIGTERM**. The watchdog
is forked with the script's `trap cleanup EXIT INT TERM` in force, and
`cleanup` is `rm -rf "$TMPROOT"`. A SIGTERM that lands before the subshell has
reset those inherited traps can run `cleanup` **inside the watchdog**, deleting
the whole fixture mid-run.

Measured in a copy of the function whose watchdog **records instead of killing**,
300 calls of `true` each:

```
kill -TERM  ->  the parent's cleanup ran inside the watchdog 18 times in 300; twice the
                watchdog then went on to its own kill line anyway
kill -KILL  ->  0 of 300; 0
```

The race was always there. This branch made it bite, because each fixture now
costs five short git calls in `make_checkout` and two fixtures five more in
`advance_origin`, and every one is a window. The fix is one word, SIGKILL for
the watchdog, which cannot be trapped, and it is the branch's **first** commit
so that no commit after it carries the race. The comment beside it carries the
measurement and its retirement condition. The tally after it is under *GREEN*:
16 of 16.

**A disclosure that belongs with this.** My first reproduction of the race,
13:52Z to 13:58Z, used the harness's watchdog as written, `kill -9` included,
before the recording copy existed: three runs in sequence, of up to four
hundred calls each. Its
marker shows 147 watchdogs running the trap, and by the 2-in-18 ratio above a
few of those will have gone on, thirty seconds later, to `kill -9` a pid that
had already exited. Whether that can hit anything else depends on pid reuse, so
I measured it rather than guessing: the counter ran from 27477 at the start,
through `pid_max` (32768) and round to about 19600 by the end — roughly 24,600
pids in six minutes, about 68 a second. Linux allocates pids in order and reuses
one only after the counter comes all the way round, which at that rate takes
about eight minutes, not thirty seconds. So those kills almost certainly found
no process. I stopped the experiment at 13:58Z, and the measurement above comes
from the copy that kills nothing. The same `kill -9`-after-trap path is in the
harness on `main` until this lands, with the same negligible reach.

## Guards added, and what retires them

Every one retires together, and each says so where it lives: **when the client
reads the queue from `origin`'s default branch rather than from a working
tree.** Then there is no checkout to be stale.

- `checkout_freshness`, `repo_freshness`, `require_current_queue`,
  `absent_item_sentence` and the calls to them in `claim`, `reconcile`, `ready`,
  `ready --set`, `done` and `doctor`.
- `routing_differs` and `require_routing`, and the calls in every command that
  pushes. They say they retire when the client reads its configuration from
  `origin`'s default branch, which is the same event.
- `cmd_fresh`, and the dispatch-time rule in `HUB.md`.
- `make_checkout` and `advance_origin` in the test, and assertions 35 to 41.
- The harness's SIGKILL of its watchdog retires on its own condition, stated
  beside it: when `run_with_timeout` stops forking a subshell to keep time, or
  the script stops trapping TERM with a handler that deletes the fixture.

## Needs Brett

This pull request changes `HUB.md`, so it is his under class 7 whatever its
checks say, and it stays a draft. Two decisions in it are his in substance, not
only by class:

1. **Strict refusal changes how dispatch works.** A primary checkout that
   another agent's merge has moved one commit makes every `claim` and `ready`
   there refuse until it is current. The message tells the agent to use its item
   worktree, created from `origin/main`, which `HUB.md` § *Isolation* already
   requires. *Recommendation: keep it strict.* The softer option — refuse only
   when the files the client reads differ from `origin`'s — was considered and
   left out, because "identical" has edge cases (untracked item files, a client
   edited in place) that a refusal on distance does not.
2. **The dispatch-time rule is a new duty for orchestrators**, in `HUB.md`.
   *Recommendation: adopt it.* It is the only part of the fix that reaches a
   checkout older than the fix, which is the case the item says is the only
   demonstration that means anything.
3. **Whether Codex threads on a pull request reserved to him are answered.**
   `HUB.md` says such a pull request "stays draft, unmerged, and unanswered",
   and the orchestrator asked this one to reply to and resolve its Codex
   thread. The register governs, so this one did not. The rule and the practice
   now differ, and one of them should move. *Recommendation:* let an agent reply
   to a Codex thread on his draft, saying how the finding was fixed, and leave
   resolving it to him. The reply is a record, and a resolve settles a matter
   that is his. That wording would go into `HUB.md` in its own change, not in
   this one.
