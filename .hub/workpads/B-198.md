**Which ref the remote schema pin names.** The card says this must not be
guessed and must be named in the pull request rather than implied by the diff.
Asked at implementation time rather than read off the card, on 2026-09-23 and on
a full clone of smn-data-pkg: the only tags are `sdp-0.2.0` and `sdp-0.3.0`, and
`f86d9b4` is `main`'s tip, sixteen commits ahead of `sdp-0.3.0` (`48c0e77`) with
none behind. So no tag carries the Q-51 ruling. The card names two options:

- **(A) Pin the commit `f86d9b4`. This is what the pull request implements.** A
  commit is as immutable as the tag was, and immutability is what the pin exists
  for. Every file the loader fetches at that commit is byte-identical to the
  vendored bundle, and it can merge without an outward act. What it gives up is
  naming a published spec release. The profile at `f86d9b4` still declares
  `sdp-0.3.0`, so the spec version metasalmon writes does not change.
- **(B) Cut a tag at `f86d9b4` and pin that.** This keeps "tracks a published
  spec version", but cutting the tag is an outward release act in smn-data-pkg,
  and yours. There is also a catch. A tag named past `sdp-0.3.0` while the
  profile inside it still declares `sdp-0.3.0` would disagree with itself. So
  (B) is really a spec-version decision, which is the question B-208 already
  holds.

**Recommendation: (A) now.** It closes the defect today and keeps the property
the pin exists to hold. The retirement condition written beside the pin moves it
to a tag on the day one exists, as a one-line change that the new byte-identity
test verifies. If you prefer (B), cut the tag and the pin moves by one line.
Nothing else in this pull request changes. Whichever ref lands, B-199 has to
match it in metasalmonpy, because a pin that differs between the two packages is
a parity divergence.
