# B-202 — A port item can reach done while the parity register still says the port is owed, and nothing checks the two against each other

## What changed, and where

A new rule in `scripts/hub_queue.py lint`: `validate_port_records()`, placed
after `validate_generated_blocks()` and called from `command_lint()`. It reads
two passages, the port section of `knowledge/parity-deviations.md` and the
mirror's section of the release index in `knowledge/roadmap.md`. For each one
separately it emits four rules:

| rule | fails when |
|---|---|
| `port-landed-unrecorded` | a port the passage names is `done` in the queue and the passage has no landed record for it |
| `port-landed-early` | a landed record belongs to an item that is not `done` |
| `port-landed-orphan` | a landed record follows no metasalmonpy id in its paragraph, so nothing can check it |
| `port-passage-missing` | the queue holds a port and a passage's file or section cannot be found |

`scripts/tests/test_hub_queue.py` gains `TestPortRecords`, which pairs a RED
and a GREEN for every rule, plus a scope test and a fence test. The module
docstring's cross-check list names the new check, and its heading no longer
carries a count.

**Why `hub_queue.py lint` and not `check-parity-registers.py`.** Lint already
parses the queue with the one item parser. Teaching the parity script to read
the queue would mean importing this module or writing a second parser of the
same files. Lint's workflow (`hub-queue.yml`) already starts on `queue/**` and
`knowledge/**`, which covers all three inputs, and it needs no sibling checkout.
The parity script exits 2 when metasalmonpy is absent, so a check placed there
would not run on a machine that has only this repository. The rule reads nothing
from `PARITY.md`.

## How it decides, and what a future port entry must contain

- **The passages are found by what they say.** No heading is matched
  literally. The register passage is every section whose heading contains both
  "owe" (owes or owed) and "mirror". The roadmap passage is every subsection of
  "Release index" whose heading names the mirror. Finding neither is
  `port-passage-missing`, so a renamed heading cannot turn the check off
  silently. A test renames the heading to 0.6.0 and shows the rule still reads
  the section and still goes RED.
- **A port is decided by the queue.** A port is an item whose `repo` is
  metasalmonpy and whose `blocked_by` names a metasalmon item, meaning the
  mirror half blocked by the R half it copies. Of the ids the two passages name,
  this picks out B-124, B-125, B-144, B-145, B-165, B-179, B-215, B-216, B-230,
  B-240, B-241 and B-242, which are the debts. It leaves out the ids the
  retirement condition excludes. B-49, B-112, B-115 and B-116 are metasalmon
  items. B-126 has no blocker. B-153 is blocked by a metasalmonpy item. Four more
  queue items match the test (B-127, B-199, B-205 and B-207, all icebox mirror
  halves), and neither passage names them yet. A list of prose phrases could not
  do this reliably. The passages name their ports as "Queued as", "its
  metasalmonpy queue item is", "its metasalmonpy half is", "the port is hub
  item", "filed in the same sweep as", "a queue item of its own" and a
  "(**B-N**, blocked by B-M" list, and the next entry's wording would slip past
  such a list with no error.
- **A landed record is `LANDED_RECORD_RE`.** It is `landed [<date>] as
  metasalmonpy [pull request] #N`, bold or not. It matches the register's
  closure form and the roadmap's marker, dated or not. The bare word "landed"
  does not match. Neither does an R half's own record, such as B-145's
  `landed 2026-09-16 as metasalmon #118`.
- **A record belongs to the nearest metasalmonpy id before it in the same
  paragraph.** Blockers and R halves are skipped, because they sit between a
  port and its record ("**B-124**, blocked by B-49 — **landed …**"). The
  paragraph limit stops a record being credited to a port in the entry above.

**So a future port entry needs:** the port's queue id, anywhere in the passage,
for its debt to be seen. Once the item is `done`, it also needs a landed record
after that id in the same paragraph. That is either
`**This one is closed.** `B-NNN` landed as metasalmonpy pull request **#NN** …`
in the register, or `` …`B-NNN`, which **landed <date> as metasalmonpy #NN**, `sha`. ``
in the roadmap. Either form is accepted in either file. Writing the record before
the item is `done` is refused.

**A defect in my own first draft, found by that positive control and not by any
failing check.** My first fence detector toggled on any leading run of backticks.
Roadmap line 696 begins with an inline code span that quotes a mermaid fence.
CommonMark says that is not a fence, because a backtick fence's info string
cannot contain a backtick. The detector took it for one, hid every heading after
it, and ran the mirror passage to the end of the file, through the other
members' sections. It now follows the CommonMark rule, and
`test_a_line_that_opens_with_an_inline_code_span_is_not_a_fence` pins it.

## What it does not check (also in the docstring)

- It does not check whether a record is true. A closure naming the wrong pull
  request, sha or date passes. It checks the shape, as
  `check-parity-registers.py` does.
- It does not check whether a port named in one passage is also named in the
  other. Each passage is checked only for the ports it names.
- It cannot see a debt described without its item's id.
- It does not require a record for mirror work that is not a port: B-201 and
  B-189 have no metasalmon blocker, and B-177 is an R-side follow-up. A record
  credited to one of them is still refused while the item is not `done`.
- It cannot catch queue state that is itself wrong. For example, an item left
  in `review` after its pull request merged still reads as owed, and the rule
  passes it.

## What I did not do, and why

- I did not edit the register, the roadmap or any queue item. The tree already
  passes. A parity-register change belongs to Brett, and the two passages had
  just been edited by the orchestrator's change.
- The rule is not in `check`. The retirement condition names `lint`.
- I made no workflow change. `hub-queue.yml` already starts on every input the
  rule reads. The rule runs only when the queue holds a port, so the unit-test
  fixtures, which hold none, need no register. On the real tree a missing file
  or section is `port-passage-missing`, not a skip.
- The retirement condition asks for a "This one is closed." paragraph in the
  register. I read that as asking for a landed record in each passage: either
  form is accepted in either file, and the literal sentence is not required. The
  sentence names no pull request, and B-165's closure varies it ("This one is
  closed, and that covers …"). The pull request number is what the rule relies
  on.

## Anything that is not this item

- **Candidate, not filed: a port named in one passage and absent from the
  other.** The retirement condition does not ask for this, and a naive check
  would be red on arrival. B-230's debt (the B-174 / B-177 ruling) is in the
  register's port section, while the roadmap's mirror section names none of
  B-174, B-177 or B-230. B-179 is named only in the roadmap, deliberately,
  because its divergence is register row 53 rather than a port-section entry.
  A check would therefore need an exemption for the row-53 shape. The
  roadmap's rule, "a new mirror debt is recorded in both places in the same
  change", is still enforced only by people reading.
- The original brief listed B-145 among the ports "already recorded as landed".
  B-145 is `review`, and no metasalmonpy commit on `origin/main` mentions B-145
  or #34. Both passages correctly carry no landed record for it, and the rule
  passes it for that reason.

## Retirement condition of the guard added

`validate_port_records()` retires when a port's landed record is no longer
hand-written prose. One way is for the item to record its pull request and both
passages to render the record as a generated block. `check` then covers it, and
this rule is deleted together with `TestPortRecords`. The same condition is in
its docstring.
