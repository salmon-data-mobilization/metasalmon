## The specification finding, for B-234

B-234's condition says whichever half lands second applies the first half's
finding. This is that finding. Every passage below was read on 2026-09-24 from
the published pages, and the rendered text was checked against the Markdown
source in `mapping-commons/sssom` on `master`.

**Question: does SSSOM forbid a `curie_map` entry that redefines a built-in
prefix to a different IRI? Yes.** The model's Identifiers section:

> By exception, prefix names listed in the table found in the IRI prefixes
> section are considered "built-in". As such, they MAY be omitted from the
> curie_map. If they are not omitted, they MUST point to the same IRI prefixes
> as in the aforementioned table.

- <https://mapping-commons.github.io/sssom/1.0/spec-model/#identifiers>
- <https://mapping-commons.github.io/sssom/dev/spec-model/#identifiers>
- source: `src/docs/spec-model.md`, line 32

**How the built-in IRIs are defined.** By the table in the introduction's IRI
prefixes section (<https://mapping-commons.github.io/sssom/1.0/spec-intro/#iri-prefixes>,
the same on `dev`; source `src/docs/spec-intro.md`, lines 19-32), which the
passage above names. The table has eight rows, in this order:

| prefix | IRI prefix |
|---|---|
| `owl` | `http://www.w3.org/2002/07/owl#` |
| `rdf` | `http://www.w3.org/1999/02/22-rdf-syntax-ns#` |
| `rdfs` | `http://www.w3.org/2000/01/rdf-schema#` |
| `semapv` | `https://w3id.org/semapv/vocab/` |
| `skos` | `http://www.w3.org/2004/02/skos/core#` |
| `sssom` | `https://w3id.org/sssom/` |
| `xsd` | `http://www.w3.org/2001/XMLSchema#` |
| `linkml` | `https://w3id.org/linkml/` |

**What a parser must do with every other prefix.** SSSOM/TSV, Identifiers
(<https://mapping-commons.github.io/sssom/1.0/spec-formats-tsv/#identifiers>;
source `src/docs/spec-formats-tsv.md`, line 116):

> all prefix names used in CURIEs MUST be declared in the curie_map slot of the
> mapping set object, unless the prefix is a "built-in" prefix (in which case it
> MAY be omitted). SSSOM/TSV parsers MUST reject a file with undeclared,
> non-built-in prefix names.

**Why every canonical file omits them.** SSSOM/TSV, *Canonical SSSOM/TSV
format*, rules for the metadata block (source line 217): a canonical writer
"MUST NOT include in the CURIE map the prefix names that are considered
'built-in'". The same section says readers "MUST NOT reject a file solely
because it does not follow the canonical rules", so the canonical form is a
writer rule, and a reader's job is only to accept it.

**Versions.** The site publishes two versions, `1.0` and `dev`, per its
`versions.json`, and `https://mapping-commons.github.io/sssom/1.1/` returns 404.
The `dev` pages describe 1.1: they say a set that carries `sssom_version` must
set it to 1.1. On PyPI, `sssom-schema` 1.0.0 (2024-08-09) is the newest stable
release and 1.1.0a5 (2026-05-22) the newest pre-release. All three passages and
the table are the same in `1.0` and `dev`; the table's HTML was diffed and is
identical. So the answer does not depend on which version metasalmon claims.

**Two lists that are not the built-in list, because the next reader may reach
for either.**

- **The SSSOM LinkML schema's `prefixes:` block** (`src/sssom_schema/schema/sssom_schema.yaml`
  on `master`) declares `dcterms`, `linkml`, `sssom`, `rdfs`, `rdf`, `oboInOwl`,
  `pav`, `prov`, `skos`, `xsd` and `semapv`. It has no `owl`, and it has four
  names the table does not. Those are the schema's own authoring prefixes. The
  schema's `curie_map` slot is optional and says nothing about built-ins.
- **sssom-py 0.4.21**, `src/sssom/context.py`: `SSSOM_BUILT_IN_PREFIXES = ("sssom",
  "owl", "rdf", "rdfs", "skos", "semapv")`. That is six names, with no `xsd` and
  no `linkml`. `ensure_converter()` chains the built-in map in front of the
  file's map "to ensure none of the SSSOM_BUILT_IN_PREFIXES are overwritten with
  non-default values". So a conflicting redefinition is silently overridden, not
  rejected. Copying sssom-py would give a different accepted set from the
  specification's in both directions. It was read as a contrast, not relied on.

**How metasalmon applies it** (`R/sssom.R`):

- `.ms_sssom_builtin_prefixes` is the table, in the specification's order. A
  test pins it.
- `.ms_sssom_validate_reference()` counts a prefix as declared if it is in the
  `curie_map` or in the table. The match is exact and case-sensitive, so `SKOS`
  is not built-in.
- `.ms_sssom_validate_builtin_prefixes()` refuses a `curie_map` entry named for a
  built-in whose trimmed expansion is not the table's. It checks every such
  entry, including one for a prefix nothing uses, because the rule is on the
  declaration. A declaration with the table's expansion is accepted. It goes
  entry by entry, so a duplicate name in an in-memory list cannot hide behind a
  correct first entry.
- That check is called from `.ms_sssom_validate_metadata()`, after the
  `mapping_set_id` and `license` checks and before the `subject_source` and
  `object_source` references. It is a validation-stage rule, not a parse-stage
  one. So it covers `read_sssom_mapping_set()` with the default
  `validate = TRUE`, `validate_sdp_sssom()`, and an in-memory set passed to
  `write_sdp_sssom()`, which is refused before anything is written.
  `validate = FALSE` skips it as it skips every CURIE check. metasalmonpy's
  `_validate_metadata()` and `_normalize_in_memory()` have the same split, so
  the placement ports one to one.
- The refusal says *redefines built-in prefix* followed by the prefix, and the
  tests match that phrase. The unknown-prefix message is unchanged.

**One correction to the item's wording.** Its condition says the reader "still
rejects" a redefinition. It did not. The old reader knew no built-ins, so a
declared `skos` with any absolute URI was an ordinary declaration and passed.
RED failures 11, 12, 14 and 15 below show it. Refusing a redefinition is new
behaviour, and `NEWS.md` says so.

## What I did not do, and why

- **metasalmonpy is untouched.** That is B-234.
- **The writer is unchanged.** It still writes whatever `curie_map` it is
  given, so a set that declares a built-in keeps it, which the canonical rules
  forbid. That is a writer rule and not this item's; see candidate 3.
- **The profile still requires a non-empty `curie_map`.** SSSOM makes the slot
  optional, and a canonical file whose every CURIE is built-in would have none.
  In an SDP mapping set, `subject_id` and `object_id` are vocabulary terms, so
  this does not arise in practice, and relaxing a required field is a separate
  decision.
- **No parity register row**, as the item says. The port section and the
  release index carry the owed port instead.

## Found, and not this item's

Candidates with no item, each checked against the queue and the backlog before
listing:

1. **`predicate_type` is validated as a CURIE, so every spec-valid value is
   refused.** `R/sssom.R` lists `predicate_type` in `.ms_sssom_reference_columns`.
   The schema gives it `range: entity_type_enum`, whose values are phrases such
   as `owl annotation property`. Reproduced on this branch: a file with that
   value in a `predicate_type` column fails with *"SSSOM predicate_type in row 1
   must be an absolute URI or compact CURIE."* `subject_category`,
   `object_category` and `similarity_measure` are listed too, and the schema
   types all three `string`. metasalmonpy's `_validate_reference()` is the same
   code.
2. **The manifest's `provenance.specification` is a dead link.** Both writers
   emit `https://mapping-commons.github.io/sssom/1.1/` (`R/sssom.R`, and
   `sssom.py:1046` in metasalmonpy), and it returns 404, because the site
   publishes only `1.0` and `dev`.
   `knowledge/plans/2026-09-14-iop-triple-explainer.md:500` cites the same URL.
3. **The SSSOM writer does not write canonical SSSOM/TSV.** The specification
   says writers SHOULD. Writing the canonical fixture, with `skos` declared,
   through `write_sdp_sssom()` gives `# ` with a space, every scalar
   double-quoted, `curie_map` last rather than second, and `skos` kept in the
   CURIE map. The package's own bytes are deterministic, which is what it means
   by canonical. Changing them moves every manifest hash and the byte-identical
   R and Python artifacts that parity row 11 rests on, so this is a design
   question, not a defect fix.

Already known, not filed: the two related notes under B-233 in the backlog
(full IRIs accepted in entity-reference slots, and `mapping_cardinality`
required on `sssom:NoTermFound` rows) are unchanged by this branch.
