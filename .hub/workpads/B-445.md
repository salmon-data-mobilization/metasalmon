## Root cause

**Not git. The runner image's `mkdir`.** The client's cap lock was taken by
`mkdir "$CAP_LOCK_DIR"`, trusting mkdir(1) to fail when the directory exists.
From 2026-10-23 the hosted runners use the `ubuntu-26.04` image, whose
`/usr/bin/mkdir` is the Rust coreutils (uutils): `rust-coreutils` 0.8.0 at the
26.04 release and `0.10.0-1ubuntu2~26.04.1` in `resolute-updates` and
`resolute-security` (Launchpad publishing history, read 2026-11-24). Its
`uu_mkdir` does this, in 0.8.0, 0.9.0 and 0.10.0 (crate sources read from
crates.io):

```rust
// create_dir()
let path_exists = path.exists();
if path_exists && !config.recursive { return Err(/* File exists */) }
// ... create_single_dir()
match create_dir_with_mode(path, mode, umask) {
    Ok(()) => { ... Ok(()) }
    Err(_) if path.is_dir() => { ... Ok(()) }     // no -p needed
    Err(e) => Err(e.into()),
}
```

0.11.0 (2026-09-01) narrowed that arm to `Err(_) if config.recursive &&
path.is_dir()`. Ubuntu's 0.10.0 changelog carries no mkdir patch. So two
processes that both pass the `exists()` check before either calls mkdir(2) both
exit 0: the loser's mkdir(2) fails with EEXIST, the path is a directory by then,
and it reports success. In `hub claim` both then believe they hold the cap lock,
both count zero live claims, and both push: **"rc 0 and 0, claim refs 2"**, in
about half a second rather than the 1.35 s a refused second claim takes,
because neither waited. The break lock (`mkdir "$CAP_BREAK_DIR"`) had the same
dependence.

**How I know.**

1. *The image, not git, is what the failures share.* Every hub-queue run in the
   300 most recent (2026-10-01 to 2026-11-24), assertion 19 read from each log
   from 2026-10-08 on:

   | image | git | runs | 19 failed |
   |---|---|---|---|
   | ubuntu-24.04 | 2.55.0 | 37 read one by one (2026-10-08 to 10-15), and 218 earlier ones whose only failure was a different assertion | 0 |
   | ubuntu-26.04 | 2.55.0 | 9 | 3 |
   | ubuntu-26.04 | 2.56.0 | 3 | 2 |
   | ubuntu-26.04 | 2.56.1 | 17 | 4, plus the first attempts of 45315478555 and 45315607136, rerun green |

   Same git 2.55.0, same empty git configuration (the test sets
   `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` to `/dev/null`): 0 failures on
   24.04, 3 of 9 on 26.04. The git-2.56 lead in the item was the image change
   seen through its git version.
2. *The mechanism reproduces with that mkdir's logic and nothing else.* A
   Python model of uu_mkdir 0.10.0's non-recursive path (exists, then mkdir(2),
   then success if the path is a directory), put first on `PATH` on this
   machine's git 2.43.0 and bash 5.2, reproduced the exact signature: "rc 0 and
   0, claim refs 2", 319 ms, the same agent token in both outputs, no break
   warning, and, past the three lines CI prints, `not releasing the claim lock
   ... it records pid 7462 rather than this process (7463)` in one output: two
   holders at once. With GNU mkdir the same loop never fails.
3. *The other suspects were read and ruled out.* git's 2.54 default maintenance
   strategy (geometric) does run `pack-refs --auto` after every fetch into the
   locks cache, but as a foreground task inside the fetch, so inside the lock;
   a lost ref update makes fetch exit 1, which the client turns into a 3, not a
   0; and the files backend reads loose refs before `packed-refs`, so a
   concurrent pack cannot hide a ref from `for-each-ref`. None of that differs
   between the two images at git 2.55.0 anyway. bash does not run an `EXIT`
   trap in a command substitution (checked), so the lock is not released early
   by a subshell.

**What I could not do, and why.** The brief asked for git 2.56 in a scratch
prefix. Building it from the kernel.org tarball (checksum verified) was refused
by this session's permission classifier, twice, and so was running the
extracted Ubuntu 26.04 `rust-coreutils` binary. Neither is needed for the
finding above, since git is ruled out by the table and the mkdir model
reproduces the signature, but the local runs below are on git 2.43.0 and GNU or
modelled mkdir, not on the runner's own binaries. The runner's own mkdir is

**Assertion 19's race, end to end, before and after.** A loop outside the tree
runs only that race: for each round a fresh locks repository and cap fixture
built as the test builds them (cap of one, two ready items, one warm-up
`doctor`), then two `hub claim` calls released through one file gate. A round
fails unless exactly one claim ref lands with one rc 0 and one rc 3. Which
`mkdir` the clients get is set by `PATH`:

| mkdir on PATH | before (d4bf85d) | after (this branch) |
|---|---|---|
| GNU coreutils 9.4 (control) | 0 of 30 | 0 of 30 |
| model of uu_mkdir 0.10.0 (Python; exists, mkdir(2), success if a directory) | **2 of 90** | 0 of 90 |
| worst case: reports success for every directory | **30 of 30** | 0 of 30 |

Every failing round had the CI signature: rc 0 and 0, two claim refs, 279 to
439 ms against a median of about 1.3 s for a passing round, and a `not
releasing the claim lock` warning in one output. After the fix every round
took 1.22 to 1.38 s, because the second claim waited and was refused.

The model's rate is lower than CI's (about one run in three) because a Python
process starts with tens of milliseconds of jitter, so two of them seldom reach
the check microseconds apart; the native binary on the runner starts in about
one. The worst case is the bound from the other side, and assertion 49 is that
worst case made deterministic.
