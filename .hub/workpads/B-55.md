## What changed, and where

- **`R/dictionary-helpers.R`, `apply_salmon_dictionary()`.**
  - The coercion now runs inside `tryCatch(..., warning = , error = )`, and
    both handlers return the condition. `strict = TRUE` aborts, naming the
    column, the type, R's reason, and each distinct value that did not convert.
    `strict = FALSE` warns with the same detail and keeps the column as
    character, which is what `@param strict` has always documented. Before
    this change it returned the `NA`s instead.
  - The codes step now warns before `factor()`. The warning names each
    distinct value that is present in the column and absent from the code
    list, under either value of `strict`. The conversion itself is unchanged.
  - Three internal helpers sit after the function.
    `.ms_apply_dictionary_coerce()` is the old if/else chain, moved verbatim so
    that the failure report can run it a second time.
    `.ms_apply_dictionary_present()` is not-NA and not-blank.
    `.ms_apply_dictionary_failed_values()` returns the values that were present
    before the coercion and are `NA` after it. It returns nothing when the
    coercion errors outright, and then R's error message is the report.
  - roxygen: `@param strict` now says a warning counts as a failure, and a
    details paragraph describes the codes report.
- **`man/apply_salmon_dictionary.Rd`** was regenerated. The local roxygen2 is
  8.1.0 and the repository's `Config/roxygen2/version` is 8.0.0.
  `devtools::document()` also bumped that field and reflowed `NAMESPACE`'s
  `importFrom` lines. Both of those were toolchain churn and were reverted, so
  only the `.Rd` file changes.
- **`tests/testthat/test-edge-cases.R`.** Three tests were replaced by five.
  **Two of the three had pinned the defect**, so they were rewritten rather
  than kept:
  - *"handles type coercion failures (strict)"* asserted that `strict = TRUE`
    **returned** with `NA`s, beside the comment *"as.integer() produces NAs and
    warnings, not errors / The function will succeed but produce NAs"*.
  - *"(non-strict)"* asserted `NA`s, beside the comment *"The function's error
    handler only triggers on actual errors, not warnings"*.
  - *"handles codes with mismatched values"* asserted only the factor class,
    and kept the comment *"Unknown becomes NA in factor"*. It is extended, not
    weakened.

  None of this narrows a test. Every replacement asserts more than the test it
  replaces. The old strict and non-strict tests asserted the behaviour that
  `@param strict` said was wrong, and the new ones assert what it says.
  The five tests are: an abort that names the value, for `integer` and for
  `number`; non-strict keeping the exact original text; missing and blank values
  not counted as failures; an erroring coercion (`as.Date("not a date")`) still
  aborting, which is a pin on behaviour that already worked; and the codes
  report under both `strict` values, which names only the present unlisted
  value, still blanks it, and stays silent for a fully listed column.

## What I did not do, and why

  work branch and the draft pull request to the item's repository.
- **`strict = TRUE` does not abort on an unlisted code value.** The retirement

## Found, not absorbed

1. **B-55's own retirement condition names metasalmonpy while its `repo` is
   `metasalmon`.** That is corollary 2 of `queue/README.md`: the item is
   claimable and unfinishable at once. The prescription there is to split it
   into a pair with an id each, each naming the other, as B-111 and B-179 were
   split. The prepared diff above is ready for the metasalmonpy half. **B-53 has
   the same shape**: its condition ends *"and metasalmonpy carries the same
   behaviour"*. That is recorded here only because it was read while choosing
   what to do. B-53 is another agent's item.
2. **Candidate: coercions that lose a value without raising any condition still
   pass `strict = TRUE`.** Measured on R 4.3.3:
   - `as.logical("yes")`, `as.logical("1")` and `as.logical("")` all return
     `NA` silently.
   - `as.Date(c("2020-01-01", "abc"))` returns `NA` for the second value
     silently. When the first value is the bad one, it errors instead.
   - `as.Date("01/02/2020")` returns `0001-02-20` silently, which is a wrong
     date rather than a missing one.
   - `as.integer("3.7")` silently truncates to `3`.
   - `as.integer(factor(c("10", "20")))` returns the factor codes `1, 2`, not
     the values.

   The mechanism that would reach all of these is a comparison of the value
   before and after the coercion, like the read path's fidelity checks. That
   needs a decision about which input tokens count as missing. metasalmonpy
   differs on every one of these cases: `astype(bool)` makes every non-empty
   string `True`, including `"no"` and `"False"`; `"3.7"` raises; and a partial
   date raises. So this is also an unregistered parity difference.
3. **Candidate, metasalmonpy: `apply_salmon_dictionary()` never applies
   `code_label`.** `dictionary.py:790` calls `rename_categories` on a `Series`,
   not on its `.cat` accessor. The `AttributeError` falls into the
   `except Exception` branch marked `pragma: no cover - defensive`, which
   converts the column to strings, so every codes application takes the
   "defensive" branch. Confirmed on pandas 3.0.5: `'Series' object has no
   attribute 'rename_categories'`. R's factor carries the labels. Python's
   `test_apply_salmon_dictionary_with_codes` asserts the categories are the code
   values, which pins the missing labels. There is a latent second defect behind
   it. The `column_role == "categorical"` block that follows rebuilds the
   categorical with `categories=code_values`, so once the labels are applied,
   that block will blank every labelled value. It is an unregistered parity
   difference. The Python intent is plain, and the test disagrees with that
   intent.
4. **B-152 reproduces here.** Both `test-github-helpers.R` errors are its
   measured 404s, on a clean branch.
