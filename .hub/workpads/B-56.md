**B-56 — Semantic retrieval issues one serial `search_fn()` call per target**
(backlog #56, stream S2). Claimed 2026-09-25 as `a-1b78ba418bed2c69`, worked on

The 2026-09-12 promotion review (`knowledge/plans/2026-09-12-queue-promotion-review.md`,
the B-56 row) asked the fix to respect three things. How each was met:

1. **The existing `find_terms()` result cache.** Not duplicated. That cache is
   session-wide, opt-in through `METASALMON_CACHE`, and only ever sees
   `find_terms()`. The dedup here is created inside one `suggest_semantics()`
   call and dropped with it, so it cannot serve an answer across calls or
   across a change of ranking settings, and it covers an injected `search_fn`.
   It neither reads nor writes `.metasalmon_cache`.
2. **The degraded-result rule.** An answer whose `diagnostics` attribute names a
   source that did not answer is returned to the row that asked and never
   stored, so the tuple's next row searches again. The test is
   `.ms_search_failed_sources()`, the one copy `find_terms()` itself uses to
   refuse caching a degraded lookup. A search that errors stores nothing, and
   the error propagates as before.
3. **The mirror.** Measured: metasalmonpy has the same defect. The port is
   recorded as owed (below).

**One design choice departs from the review row's wording, deliberately.** The
row says to dedupe over "query, role and sorted sources". The key here is the
arguments exactly as `search_fn` receives them, sources in their given order.
Within one call a role's sources are one fixed vector
(`.ms_sources_for_target_role()` is a function of the call's source policy and
the role), so sorting would merge no additional rows; and it would assume an
injected `search_fn` ignores source order, which nothing guarantees.
`find_terms()` sorts for its own key because it knows its own behaviour; this
layer does not know the function it wraps.

## What changed, and where

- `R/semantics-helpers.R`: new `.ms_search_once_per_call(search_fn)`, and
  `suggest_semantics()` hands it, instead of `search_fn`, to the first-pass map
  over targets. Nothing is hashed. The kept answers are narrowed by query
  string, compared in C, and a hit counts only when the whole argument list is
  `identical()`. A hash would need an rlang newer than the unversioned import
  promises, or the serialiser, which rlang 1.3.0's NEWS records hashing
  identical objects differently on R 4.6.0. A call whose query is not a single
  string passes straight through and is never kept, and a `NULL` answer is kept
  like any other. Measured in the wrapper alone: 3,000 calls over 1,500
  distinct queries took 0.52 s. The two LLM retry passes
  (`R/llm-semantic-helpers.R`, `R/semantic-bundle-review.R`) still receive the
  raw `search_fn`, unchanged.
- `tests/testthat/test-semantic-retrieval-dedup.R`, new. It counts the calls on
  a duplicate-heavy fixture: four tables carrying the same two columns, 40
  targets and 9 distinct tuples. It asserts no tuple is searched twice, no tuple
  is missed, and every row's candidates are `identical()` to per-row
  retrieval's, in the same order. For the degraded rule, a degraded first answer
  stays with its own row, the tuple's next row searches again, the full answer
  is then shared, and during an outage every row searches for itself.
- `tests/testthat/test-dictionary-helpers.R`, "keeps biological qualifiers in
  count-like variable queries". It counted `search_fn` calls per query to learn
  how many columns derive each query, and dedup changes that instrument. The
  multiplicity assertions now read `attr(res, "semantic_targets")`, which records
  what every target asks for. All five original assertions are kept, and the
  set assertion is also kept on the call log.
- `NEWS.md` (development version, Fixed), `knowledge/backlog.md` (#56's R half
  recorded as fixed), `knowledge/parity-deviations.md` (port section) and
  `knowledge/roadmap.md` (release index): the port owed, not a register row.
